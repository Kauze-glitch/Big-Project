# ZYRO Volleyball Club Form

Mobile-first registration form for ZYRO Volleyball Club. It replaces Google Forms with a branded public form, stores submissions in Supabase Postgres through a private Edge Function, and includes a password-protected admin page.

## Local run

```bash
npm install
npm start
```

Open `http://localhost:3000`.

Admin: `http://localhost:3000/admin.html` (also available at `/admin`). The username defaults to `zyro`; the production password is not stored in the browser or repository, and the Edge Function verifies its SHA-256 hash.

## Render

The current Render workspace has two services on branch `zyro-club-form-deploy`:

- Static site `zyro-volleyball-club`, publishing `zyro-club-form/public` at `https://zyro-volleyball-club.onrender.com`.
- Node Web Service `zyro-club-form`, running the Express server from `zyro-club-form`.

Both services use the existing `Kauze-glitch/Big-Project` repository. Persistent registrations and site configuration live in Supabase, so content edits do not require rebuilding the public site.

Public form fields:
- Zalo name
- Expected participation duration
- Gender, volleyball position, current level
- Goal when joining a match
- Optional email address for an approval or rejection notification

After submission, the success screen renders the admin/contact list from `zyro_site_config` and creates Zalo links from each phone number.

The public page uses the ZYRO club logo as its only image asset; there is no stock volleyball gallery or footer.

## Admin CMS

The site includes `/admin.html`. Admins can review registrations and edit the public site's hero copy, play schedule, club principles, contacts, confirmation copy, and form options. Public content is stored in Supabase `zyro_site_config` and loaded at runtime, so changes such as adding T4/T6 or another deputy contact do not require a code deploy. The Admin UI refreshes data in place, reports async results, and tracks unsaved configuration changes. Registration deletion and individual approval/rejection are handled by the authenticated `zyro-api` Edge Function.

## Approval and rejection email

The Admin settings screen includes editable approval and rejection email templates, HTML formatting, merge fields, brand colors/logo and a live preview. When an admin approves or rejects an individual registration, the decision dialog can send the saved template or a one-off custom message. Rejection-by-template requires a per-applicant reason and the `{{reason}}` merge field. A one-off custom rejection never overwrites the saved template. Bulk actions can only return selected registrations to `new`; approvals and rejections must be handled individually so the admin can review the message.

Email delivery uses a free Google Apps Script Web App relay with `MailApp.sendEmail`. Render calls the Google endpoint over HTTPS; no SMTP ports, Nodemailer, Gmail App Password, paid Render plan, or third-party email provider is required. See [`google-apps-script/README.md`](google-apps-script/README.md) for the one-time setup.

Set these server-only variables in Render → `zyro-club-form` → Environment:

- `MAILER_WEB_APP_URL`: deployed Google Apps Script Web App URL ending in `/exec`.
- `MAILER_SHARED_SECRET`: random secret generated by `setupZyroMailerSecret` and stored in the Apps Script Script Properties.
- Keep `ZYRO_API_URL` as currently configured.

The Apps Script must execute as the deploying Gmail account and allow anonymous web-app access; the long shared secret authenticates calls from Render and is never exposed to browser code. Admin can check the relay, see Google's live remaining daily recipient quota, and send a test email. Consumer Gmail currently has a published 100-recipient/day Apps Script quota; Workspace accounts have different quotas and Google may change them.

The decision-email outbox is `public.zyro_decision_email_outbox`. It stores only the idempotency key, registration ID, decision, delivery state and internal Google Apps Script receipt ID; it does not store recipient addresses or rendered email content. RLS is enabled and only `service_role` has table privileges. If Google accepts an email but saving the registration decision fails, retrying the same request reuses the saved outbox record and does not send the email again. The Apps Script retains hashed idempotency keys and send states for 30 days; Supabase allows retries for 29 days, so a quota-exhausted request can be retried after Google's daily quota resets while uncertain sends remain blocked.

## Draft Zalo member mapping

The Admin page includes **Mapping Zalo**. It loads every Form registration (regardless of `new`, `approved` or `rejected` status), reads the selected Draft account's groups and the group's verified Zalo member directory, then previews name matches. A single exact name match can be preselected; duplicate or similar names require an Admin choice. A saved Zalo UID takes precedence over later display-name changes and is revalidated against the selected group's current directory.

Only the Form's gender, volleyball position and level are sent to Draft. Participation duration and the applicant's goal remain in `zyro_registrations`. Draft uses the verified member's own Zalo display name and avatar, fills missing profile fields, and preserves values already confirmed in Draft. The directory must be complete before any mapping is saved or synchronized. Changing a previously saved UID requires an explicit confirmation; the old Draft profile is not automatically deleted.

The Form-to-Draft request runs through the authenticated Node Admin routes and the existing `zyro-api` Supabase Edge Function. The shared key is read only by the Edge Function and is never sent to browser code. Generate one key with `openssl rand -hex 32`, then configure the same value in both places:

- Draft Render service: `ZyroMapping__InternalKey`.
- Supabase Edge Function secrets: `ZYRO_MAPPING_INTERNAL_KEY` and `DRAFT_API_BASE_URL` (the HTTPS origin of the Draft API, without a path suffix).
- Draft Render setting `ZyroMapping__AdminUserId` is optional when exactly one Draft admin owns a connected Zalo account. Set it only when multiple connected owners exist, to restrict which account is shared with ZYRO.

Apply `supabase/migrations/20261103160715_zyro_registration_zalo_mapping.sql` before deploying the updated Edge Function. It adds the confirmed UID, selected group/connection, mapping state and audit fields to `public.zyro_registrations`; it does not add a unique UID constraint or change existing registration statuses. After configuring the secrets listed below, deploy the `zyro-api` Edge Function and the `zyro-club-form` Render service/static site together. Do not expose `ZYRO_MAPPING_INTERNAL_KEY` or `ZyroMapping__InternalKey` in Render static-site variables or browser JavaScript.

The `zyro-api` Edge Function is deployed independently to Supabase project `grhdawkxnrkgkahegnnd`. Keep the SHA-256 hash of the existing ZYRO Admin password in the Supabase Function Secret `ADMIN_PASSWORD_SHA256`; the function reads it from the runtime environment and fails closed when it is missing. Never commit the hash or the plaintext password to GitHub. If the secret is not already configured, generate the hash locally from the current Admin password before deploying this source.
